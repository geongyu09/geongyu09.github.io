> 이 문서는 실제 블로그 초안을 작성할 때 참고하기 위한 **재료 정리 문서**다.

## 1. 톤앤매너 체크리스트 (작성 시 반드시 확인)

1. 모든 평서문이 "~다" 체로 끝나는가? (description 필드는 예외)
2. 주어가 "나"로 되어 있는가? "필자", "저자" 같은 표현이 없는가?
3. "나"가 나올 때마다 **감정이 아니라 분석**이 뒤따르는가?
4. 한 문단에 긴 문장과 짧은 문장이 섞여 있는가?
5. 코드 블록 앞뒤에 "왜 이 코드가 필요한지" + "그래서 무엇을 했는지"가 붙어 있는가?
6. 코드 블록 안에 한글 주석이 있는가?
7. 다이어그램마다 "이 그림이 보여주는 것"에 대한 해설이 붙어 있는가?
8. 접속 부사("그러다 보니", "게다가", "하지만")가 자연스럽게 흐름을 이어주는가?
9. 각 섹션 안에서 "공식"과 "추정(소스 분석)" 파트가 시각적으로 구분되는가?
10. 강조 부사("정말로", "너무나도")가 한 문단에 2번 이상 나오지 않는가?

### 분석적 '나'의 예시 톤

- ✅ "나는 이 루프 구조가 흥미롭다고 생각한다. 왜냐하면..."
- ✅ "나는 이 지점에서 설계자의 의도가 드러난다고 본다."
- ❌ "나는 Claude Code를 처음 썼을 때 엄청 신기했다." (감정)
- ❌ "Claude Code는 에이전트 하네스로 동작한다." (일인칭 없음, 논문 톤)

### [# 1부: 왜 모델만으로는 부족한가]

**길이**: 약 1,200자

**목표**: 독자가 "아, LLM만 있어서는 안 되는구나. 뭔가를 감싸야 하는구나"를 체득하게 만든다.

#### 1-1. LLM이 할 수 있는 것, 할 수 없는 것

- 공식 문서 인용: "도구가 없으면 Claude는 텍스트로만 응답할 수 있다"
  - 출처: `_클로드_공식문서__claude_code의_작동_방식`
- 소스 분석 인용: "Claude AI는 그 자체로는 텍스트만 생성할 수 있다. 파일을 읽거나, 코드를 실행하거나, 인터넷을 검색하는 것은 불가능하다. 그래서 Claude Code가 '다리' 역할을 한다."
  - 출처: `클로드_코드_소스_코드_7._도구_Tool__시스템`

#### 1-2. "일하는 LLM"에 필요한 네 가지 제공물

- 컨텍스트 (무엇을 알고 시작할 것인가)
- 도구 (무엇을 할 수 있게 할 것인가)
- 루프 (어떻게 반복시킬 것인가)
- 상태 (무엇을 기억할 것인가)
- **이 네 가지를 제공하는 것이 하네스의 역할이라는 선언**

#### 1-3. 하네스라는 이름

- "하네스"의 어원 — 말에 씌우는 마구, 사람에게 씌우는 안전 벨트
- 모델의 지능을 '구속'하는 게 아니라 '실제로 일을 하게끔 방향을 잡아준다'는 의미
- 공식 문서의 정의 재인용
- **분석적 '나'**: "나는 하네스라는 단어 선택이 매우 정확한 비유라고 생각한다."

### [# 2부: 에이전트 루프 — 하네스의 심장]

**길이**: 약 1,500자 (가장 중요한 섹션)

**목표**: 독자가 "아, 이게 단순 API 호출이 아니라 루프구나"를 완전히 이해하게 만든다.

#### 2-1. 공식 문서가 말하는 세 단계 — 컨텍스트 수집 → 작업 수행 → 결과 검증

- 출처: `_클로드_공식문서__claude_code의_작동_방식`
- 공식 다이어그램 참조 (agentic-loop.svg 언급만)

#### 2-2. API 레벨에서 실제로 생긴 모양 — `while stop_reason == "tool_use"`

- 인용: Anthropic API 공식 문서
  - "The canonical shape is a while loop keyed on stop_reason"
  - 출처: https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works
- **JS 의사코드 블록** 삽입:

```javascript
// 에이전트 루프의 본질 — 이것이 하네스의 심장이다
async function agentLoop(userMessage, tools) {
  // 대화 이력에 사용자 메시지 추가
  const messages = [{ role: 'user', content: userMessage }];

  // 루프의 종료 조건은 오직 하나 — stop_reason이 tool_use가 아닐 때
  while (true) {
    // 1. API에 현재까지의 대화와 도구 스키마를 보낸다
    const response = await client.messages.create({
      model: 'claude-opus-4-7',
      messages,
      tools,
    });

    // 2. 응답을 대화 이력에 추가한다
    messages.push({ role: 'assistant', content: response.content });

    // 3. 모델이 도구를 쓰지 않았다면 루프 종료
    if (response.stop_reason !== 'tool_use') {
      return response;
    }

    // 4. 도구를 썼다면 실행하고 결과를 다시 대화에 붙인다
    const toolResults = await executeTools(response.content);
    messages.push({ role: 'user', content: toolResults });
    // 루프 맨 위로 돌아간다
  }
}
```

- **이 코드가 왜 중요한가**: "이 while 루프 하나가 LLM을 에이전트로 만드는 핵심이다"

#### 2-3. Claude Code가 실제로 구현한 한 턴의 내부 — 5단계

- 출처: `클로드_코드_소스_코드_5.2_턴_Turn_의_처리_흐름`
- **삽입 다이어그램**: 턴 처리 5단계 전체 ASCII 다이어그램 통째로 인용
  1. Message Preprocessing (Snip / Micro / Collapse / Auto-Compact)
  2. API Streaming Call
  3. Error Withholding & Recovery
  4. Tool Execution
  5. Post-processing (Stop Hooks, 예산 체크, 루프 재진입 결정)

#### 2-4. 드라마틱 디테일 3가지

- **Auto-Compact 임계값은 `context_window - 13000`** — 왜 하필 13000인가에 대한 관찰
- **413 (Prompt Too Long) 에러 복구 3단계**: collapse drain → reactive compact → fail
- **max_tokens 초과 시 8K → 64K로 에스컬레이션, 최대 3번 재시도**
- 모두 출처: `클로드_코드_소스_코드_5.2_턴_Turn_의_처리_흐름`

#### 2-5. 구체적 예시 — "auth.ts의 버그를 고쳐줘"

- 소스 분석 문서의 Turn 1~4 예시 그대로 인용 (FileRead → FileEdit → Bash → 최종 응답)
- 출처: `클로드_코드_소스_코드_5.2_턴_Turn_의_처리_흐름`

#### 2-6. 비동기 제너레이터 패턴 언급

- "레스토랑 비유" 인용 — 모든 음식이 준비될 때까지 기다리는 대신 준비되는 대로 내오는 방식
- 스트리밍 응답이 왜 UX에 중요한가
- 출처: `클로드_코드_소스_코드_4._시작과_초기화_과정` (query.ts 설명 부분)

**분석적 '나' 지점**: "나는 이 루프 구조가 아주 단순하다는 점이 오히려 놀랍다. 복잡성은 루프 안에 있다."

### [# 결론: 하네스라는 관점에서 보면]

**길이**: 약 400~600자

**목표**: 글 전체를 관통한 독자에게 "하네스 설계의 보편 원칙"을 4가지로 남긴다.

#### 관찰한 설계 원칙 4가지 (초안)

1. **모델과 하네스를 분리한다** — 모델은 텍스트만 생성하고, 나머지는 전부 바깥에서.
2. **루프는 단순하게, 루프 안쪽은 정교하게** — `while stop_reason == "tool_use"` 한 줄 안에 온갖 복잡성이 숨어있다.
3. **안전한 것은 빠르게, 위험한 것은 천천히** — 동시성과 권한 설계의 일관된 원칙.
4. **컨텍스트는 주머니가 아니라 자원** — 능동적으로 관리하고 압축한다.

#### 마무리 문장의 방향

- 분석적 '나'로 닫는다: "나는 Claude Code가 LLM 애플리케이션 설계의 교과서적 사례라고 본다."
- 다음 주제 예고는 선택사항 — 작성 시점에 결정

## 11. 작성자(다음 세션의 Claude 혹은 사용자)를 위한 메모

- 이 글은 **순수 분석 글**이다. 개인 경험 서사는 빼고, 분석적 '나'만 쓴다.
- 글의 신뢰도를 결정하는 건 "공식"과 "추정(소스 분석)"의 **시각적 구분**이다. 섞이면 안 된다.
- 입문자 대상이라고 해서 표면만 다루면 안 된다. 중간 아키텍처 레이어(10단계 파이프라인 등)까지 들어가는 것이 이 글의 약속이다.
- 다이어그램은 일단 최대한 넣는다. 검수 단계에서 솎아내는 편이 사후에 "아 그때 그 다이어그램을 넣을 걸" 하고 후회하는 것보다 낫다.
- "~다" 체와 "나"의 조합이 어색하면 한 번 소리 내어 읽어본다. 톤앤매너 가이드의 관용구(6번 섹션)를 참고한다.
- 톤앤매너 가이드의 블로그 어미는 "~다" 체지만, 프론트매터의 `description` 필드만 예외로 "~습니다" 체를 쓴다는 점 잊지 말 것.
