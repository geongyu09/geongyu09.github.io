# geongyu09 블로그 글쓰기 가이드

이 스킬은 geongyu09가 자신의 블로그에 글을 쓸 때 일관되게 유지하는 말투, 호흡, 구조를 담는다. 크게 두 종류의 글이 있으며 둘은 톤이 조금 다르지만, 근본적인 서술 습관은 공유한다.

- **기술 포스트**: 프로젝트에서 마주친 문제를 정의하고, 시도한 해결책과 그 근거를 설명하고, 결과를 보여주는 글.
- **회고 글**: 한 해, 혹은 특정 경험을 되돌아보며 감정과 배움을 정리하는 글.

두 경우 모두 "개발자가 독자에게 자신이 겪은 여정을 솔직하게 털어놓는" 톤을 유지한다.

## 1. 말투와 문체

### 기본 어미

모든 글은 **"~다" 체**로 작성한다. "~습니다", "~해요"는 사용하지 않는다. 블로그 상단 프론트매터의 `description` 필드는 예외적으로 "~습니다" 체를 쓴다(예: "시도를 녹여보았습니다!").

```
O: 이번에 웹뷰로 프로젝트를 진행하면서 일반적인 웹의 네비게이션 방식은 정말로 정말로 사용성에 치명적이라는 생각이 들었다.
X: 이번에 웹뷰로 프로젝트를 진행하면서 일반적인 웹의 네비게이션 방식은 정말 사용성에 치명적이라는 생각이 들었습니다.
```

### 일인칭 주어

주어는 **"나"**를 그대로 쓴다. "필자", "저자" 같은 표현은 쓰지 않는다. 주어를 생략해도 자연스러우면 생략한다.

```
O: 나는 항상 무언가 개발을 할 때에는 이미 개발이 되어있다고 생각하고 사용하는 로직을 먼저 작성해둔다.
O: 처음에는 이 문제를 모든 스크린 네비게이션의 책임을 앱에 두면 되지 않을까?라고 생각했었다.
```

### 호흡 — 의식적으로 긴 문장과 짧은 문장을 섞는다

한 문단 안에서 문장 길이를 의도적으로 변주한다. 배경이나 맥락을 설명할 때는 문장을 길게 늘이고, 감정이나 결론을 찍을 때는 아주 짧게 끊는다.

```
긴 문장(맥락 쌓기):
"그동안 웹 개발만 하던 내가 처음으로 앱 개발을 하면서 들었던 생각은 생각보다 앱은 사용성을 위하여 정말 디테일한 부분까지 신경을 써야 한다는 것이었다."

짧은 문장(감정/결론 찍기):
"바로 우리 프로젝트에 적용을 시켜보려고 했다."
"아쉽기도 했지만, 기왕 이렇게 된 거 내가 만들어버려야겠다고 생각을 했다."
```

### 구어체 표현을 섞는다

딱딱한 기술 문서가 아니라 사람이 말하는 톤이다. 다음과 같은 표현들을 적극적으로 쓴다.

- **강조 부사 반복**: "정말로 정말로", "너무나도", "엄청", "되게"
- **자문자답/독백**: "~가 아닌가 생각한다", "~지 않을까?", "~라고 생각했다"
- **감탄**: "아쉽기도 했지만", "정말 뿌듯해서", "너무 기뻐서"
- **회상 투**: "~했던 기억이 있다", "~했던 것 같다", "돌이켜보면"

### 이모지는 감정 포인트에만

이모지는 문단 끝이나 소제목 끝에 한 번씩만 쓴다. 남발하지 않는다. 주로 아래 이모지들을 쓴다.

- 🥲 (아쉬움/답답함)
- 🤔 (의문/고민)
- ✍️ (쓰기/작성)
- 😅, 😭 등은 거의 쓰지 않음

```
O: "게다가 일반적인 웹은 뒤로가기가 없는 iOS에서 뒤로가기를 할 수가 없다는 문제도 존재한다. 🥲"
O: "## 앱은 어떻게 전환할까? 🤔"
```

### 자주 쓰는 어휘와 패턴

| 상황                    | 쓰는 표현                                                       |
| ----------------------- | --------------------------------------------------------------- |
| 어떤 생각이 떠올랐을 때 | "~라고 생각하였다", "~가 먼저 떠올랐다", "~지 않을까 생각했다"  |
| 시도했을 때             | "~해보았다", "~하도록 하였다", "~해주었다"                      |
| 결과 확인               | "실제로도 잘 동작하는 것을 볼 수 있다!", "~을 확인할 수 있었다" |
| 문제 인지               | "~라는 것을 깨달았다", "~문제가 발생했다", "~이슈가 있다"       |
| 회상/회고               | "돌이켜보면", "지금 생각해보면", "~했던 것 같다"                |

### 느낌표는 아끼지 않되, 남발하지 않는다

감정이 실린 문장 끝에는 느낌표를 쓴다. 단, 한 문단에 2개 이상은 피한다.

```
O: "실제로도 잘 동작하는 것을 볼 수 있다!!"
O: "이름 또한 `<Link/>`에서 영감을 얻었다."
```

## 2. 글의 전개 구조

### 기술 포스트의 기본 골격

기술 포스트는 거의 항상 아래 순서를 따른다.

1. **배경 / 문제 제기 (도입)** — "어떤 맥락에서 이 문제를 만났는지"
2. **첫 번째 시도와 그 한계** — 순진하게 시도해본 방법과, 왜 그 방법이 부족했는지
3. **레퍼런스 탐색** — 다른 사람들은 어떻게 하는지 찾아봄 (있으면)
4. **직접 만들기로 결심** — 문제 재정의, 목표 설정
5. **구현 과정** — 아이디어 → 형상 그림 → 핵심 로직 → 결과 확인. 이 사이클을 기능별로 반복
6. **발견된 이슈와 임시방편** — 구현 이후 드러난 문제들
7. **결론 / 회고** — 이번 프로젝트가 나에게 어떤 의미였는지

이 구조를 지키되, 각 단계의 분량은 내용에 맞게 조절한다.

### 회고 글의 기본 골격

회고 글은 좀 더 자유롭지만 다음 리듬을 탄다.

1. **연/시기를 한마디로 규정하며 시작** — "잘가라 파이썬의 해", "올 한해는 ~"
2. **왜 이 회고를 쓰는지, 어떤 마음으로 쓰는지 짧게 고백**
3. **시간순 혹은 주제별로 섹션을 나눠 서술** — 각 섹션은 사건 → 내가 느낀 것 → 배운 것 순으로 전개
4. **마지막에 미래에 대한 감정 (불안, 기대, 다짐)을 솔직하게 털어놓음**

### 문단 내부의 전개 — "사실 → 나의 생각 → 부연"

한 문단 안에서도 패턴이 있다. 먼저 사실/상황을 짧게 진술한 뒤, 거기에 대한 나의 생각이나 판단을 덧붙이고, 마지막에 부연이나 여운을 남긴다.

```
예시:
[사실] "처음 라이브러리를 만들었을 때는 너무 신나서 주변 사람들에게 자랑하고 다녔었다."
[생각] "지금 돌이켜보면, 앱 개발이나 RN에 대해 아는 게 많지 않았기 때문에 가능했던 부분도 있었던 것 같다."
[부연] "'이걸 처음 쓰는 입장에서 왜 이게 없지?'라는 생각에서 출발한 개발이 많았다."
```

### 인용 형식의 사고 과정을 자주 넣는다

스스로에게 던진 질문이나 당시에 했던 생각을 **따옴표로 감싸서** 그대로 노출시킨다. 이게 글에 생동감을 준다.

```
O: 처음에는 이 문제를 "모든 스크린 네비게이션의 책임을 앱에 두면 되지 않을까?"라고 생각했었다.
O: "이걸 처음 쓰는 입장에서 왜 이게 없지?"라는 생각에서 출발한 개발이 많았다.
```

### 접속 부사 — 호흡을 이어붙이는 장치

문단과 문단 사이, 혹은 문장과 문장 사이에 아래 접속 부사들을 자주 쓴다. 글의 흐름이 "천천히 같이 생각해보자"는 톤이 되게 만드는 핵심 장치다.

- **"그러다 보니"**, **"그러다가"** — 자연스럽게 다음 단계로 넘어갈 때
- **"게다가"** — 문제나 이유를 하나 더 쌓을 때
- **"하지만"**, **"그럼에도 불구하고"** — 반전
- **"이에 따라서"**, **"이를 통해서"** — 논리적 전환
- **"결론적으로"** — 정리할 때

## 3. 제목과 소제목

### 프론트매터

모든 글은 YAML 프론트매터로 시작한다.

```markdown
---
title: '웹을 앱처럼 만들어 보자!'
date: '2025년 7월 30일'
description: '웹뷰 개발 중 웹에 앱 화면 전환 효과를 주기 위한 시도를 녹여보았습니다!'
thumbnail: '/assets/blog/appLikeWeb/webAppComp.gif'
tags: 'webview animation react next.js library'
timeStamps: 1753833600000
---
```

- `title`: 구어체로 작성하며 느낌표로 끝나는 경우가 많다. 회고 글은 `[회고]` 프리픽스를 붙인다.
- `description`: 앞서 말했듯 이 필드만 "~습니다" 체를 쓴다.
- `tags`: 공백으로 구분한 단어들 (배열 X).

### H1 (`#`)

H1은 글의 최상단에 **제목과 동일하거나 거의 같게** 한 번 더 쓴다. 그리고 큰 섹션 구분에도 `#`를 쓴다. 즉 H1은 여러 개 나올 수 있다.

```markdown
# 웹을 앱처럼 만들어 보자!

...

# 라이브러리를 만들자

...

# 결론
```

### H2 (`##`)

H2는 큰 섹션 안의 주제 구분이다. 의문문이나 구어체 서술형을 쓰는 경우가 많다.

```markdown
## 앱은 어떻게 전환할까? 🤔

## 개발 시작

## 전환 효과 만들기\_fade

## iOS 뒤로가기
```

### H3 (`###`)

H3은 구현 단계나 하위 주제다. 언더스코어를 이용해 대주제와 소주제를 묶는 습관이 있다(`### 전환 효과 만들기_slide`, `### 구현하기_slide`).

### 인용구 블록 (`>`)으로 안내문 쓰기

글 초반에 자주 인용구 블록으로 **독자를 위한 안내**를 적는다. 포스트 코드 원본 링크, 관련 PR, 영상 링크 등.

```markdown
> 해당 포스트는 설명을 위하여 다소 생략된 코드가 존재할 수 있습니다.
> 모든 코드는 [여기](URL)에서 확인할 수 있습니다!
> 관련 pr : [제목](URL)
```

회고 글에서는 섹션 끝에 관련 글이나 영상을 `>` 블록으로 덧붙이는 패턴도 있다.

```markdown
> **[관련 글]**
> 웹뷰 브리지 라이브러리 개발 기록 : URL
> 웹을 앱처럼 만들어 보자! : URL
```

## 4. 코드 블록 사용 방식

### 언어 태그를 반드시 붙인다

코드 블록은 반드시 언어 태그를 붙여 하이라이팅을 살린다. 가장 많이 쓰는 태그는 `tsx`, `typescript`, `javascript`다. 단일 JS 스니펫에는 `javascript`, 타입이 드러나는 코드에는 `typescript`, React 컴포넌트 전체에는 `tsx`.

### 코드는 "완성본"보다 "핵심 로직"을 보여준다

전체 파일을 그대로 붙이지 않는다. 설명에 필요한 핵심 부분만 보여주고, 생략된 부분은 `// ...`로 처리한다. 이 방식이 가독성이 훨씬 좋다.

```tsx
authenticatedApi.interceptors.request.use(
  async (config) => {
    if (isInStackFrame()) {
      await new Promise((resolve) => setTimeout(resolve, 99999));
    }

	// ...

    return config;
  },
  ...
);
```

### 코드 내부에 한글 주석을 적극적으로 쓴다

코드 블록 안에 **한글 주석**으로 각 줄이 하는 일을 설명한다. 이게 작성자만의 큰 특징이다. 주석은 단순 번역이 아니라 **의도**를 담는다.

```tsx
// 사용자가 <StackLink /> 를 클릭할 때 실행할 콜백 함수
const slideScreen = useCallback(() => {
  // stack-main을 가져온다.
  const main = document.getElementById("stack-main");

  // 슬라이드 애니메이션을 선택했다면
  if (animation === "slide") {
    // stack-main을 살짝 왼쪽으로 이동시킨다.
    main.style.transition = `transform ${animDuration}ms ease-in-out`;
    main.style.transform = "translateX(-20%)";
    ...
  }
}, [animation, href, push, router]);
```

### 코드 앞뒤에 "왜/무엇을" 문장을 붙인다

코드 블록은 결코 단독으로 등장하지 않는다. 바로 앞에는 "이 코드가 왜 필요한지"를, 바로 뒤에는 "그래서 이 코드가 무엇을 했는지"를 짧게 덧붙인다.

````markdown
[앞] 이 아이디어를 바탕으로 핵심 로직을 작성해보았다.

```tsx
코드;
```
````

[뒤] 전환 애니메이션이 올바르게 들어가는 것을 확인할 수 있었다.

````

### 인라인 코드(`` ` ` ``)로 컴포넌트·함수·용어를 감싼다

본문 중간에 컴포넌트명, 함수명, CSS 속성, id 값 등은 모두 백틱으로 감싼다. `<StackLink />`, `<div />`, `transform-transition`, `stack-main` 처럼.

## 5. 이미지와 외부 자료 사용

### 이미지 경로 규칙

이미지는 `/assets/blog/<포스트-slug>/<파일명>` 경로에 둔다. alt 텍스트는 한글로 "무엇을 보여주는 이미지인지"를 설명적으로 쓴다.

```markdown
![웹과 앱의 전환 효과 확인](/assets/blog/appLikeWeb/webAppComp.gif)
![네비게이션의 책임을 앱으로 둔 경우](/assets/blog/appLikeWeb/navigateWithBridge.gif)
![slide 전환 애니메이션 형상그림](/assets/blog/appLikeWeb/image-289.png)
````

### 이미지 뒤에는 "무엇을 보여주는지"를 해설한다

이미지는 삽입하고 끝이 아니다. 바로 아래에 **그 이미지가 보여주는 것**과 **그래서 어떤 점을 주목해야 하는지**를 산문으로 풀어 쓴다.

```markdown
![웹과 앱의 전환 효과 확인](/assets/blog/appLikeWeb/webAppComp.gif)

위의 영상에서 볼 수 있듯 클릭을 한 시점에서 웹은 아래의 절차대로 화면을 보여준다.

- 이전 화면이 잠시 보인다.
- 이동하고자 하는 url로 이동한다. ...
```

형상 그림(설계 스케치)을 많이 활용한다. 코드로 구현하기 전에 "내가 그리고 있는 형상 그림"을 먼저 보여주고, 그 다음 코드로 넘어가는 흐름이 자주 등장한다.

### 외부 링크

- 기술 포스트의 레퍼런스(MDN, Next.js 공식문서 등)는 직접 캡처한 이미지로 첨부하고 alt 텍스트에 출처를 밝힌다: `![Next 공식문서 Link 태그 설명 중](...)`
- 본인이 만든 라이브러리/PR/깃허브는 인용구 블록이나 본문 링크로 둘 다 등장한다.
- 외부 도구(스택플로우, expo 등)는 본문 링크로 언급한다: `"[스택 플로우](https://stackflow.so/)"`

### 구분선 `---` 으로 큰 흐름을 나눈다

기술 포스트에서 "문제 제기"가 끝나고 "본격 구현"으로 넘어갈 때, 혹은 "구현"이 끝나고 "회고"로 넘어갈 때 `---`으로 한 호흡 끊어준다.

## 6. 자주 쓰는 관용 구절 모음

직접 글을 쓸 때 아래 구절들이 자연스럽게 등장한다. 참고용 레퍼런스.

**도입부에서 자주 쓰는 시작**

- "그동안 ~만 하던 내가 처음으로 ~을 하면서 들었던 생각은 ~이었다."
- "이번에 ~을 하면서 ~라는 생각이 들었다."
- "나는 항상 무언가 개발을 할 때에는 ~"

**문제를 인식했을 때**

- "하지만 개발을 진행해나감에 있어 해당 방법이 정말 큰 문제점이 있다는 것을 깨달았다."
- "~라는 것을 알게 되었다."
- "이를 그대로 서비스에 적용하기에는 무리가 있다."

**해결책을 고를 때**

- "가장 좋은 방법은 ~이겠지만, 현 상황에서 임시방편으로 ~"
- "~을 목표로 잡고 개발을 시작했다."
- "~라고 생각하였다. 이에 따라서 ~"

**결과 확인**

- "실제로도 잘 동작하는 것을 볼 수 있다!!"
- "~을 확인할 수 있었다."

**결론부**

- "이번 프로젝트를 하면서 정말 많은 시도를 할 수 있어서 좋은 것 같다."
- "아직 완벽하지는 않다. ~를 TODO로 가져갈 예정이다."

**회고 글의 감정 서술**

- "~했던 기억이 있다."
- "~했을 때는 정말 멋지다는 생각이 들었다."
- "~지 않았나 싶다."
- "그럼에도 불구하고, ~"

## 7. 글을 쓸 때 체크리스트

글을 완성한 후 다음을 점검한다.

1. 모든 평서문이 "~다" 체로 끝나는가? (description 필드는 예외)
2. 주어가 "나"로 되어 있는가? "필자", "저자" 같은 표현이 없는가?
3. 한 문단에 긴 문장과 짧은 문장이 섞여 있는가? 너무 딱딱하지 않은가?
4. 코드 블록 앞뒤에 "왜 이 코드가 필요한지"와 "그래서 무엇을 했는지"가 붙어 있는가?
5. 코드 블록 안에 한글 주석이 있는가?
6. 이미지마다 한글 alt 텍스트와 해설 문장이 있는가?
7. 접속 부사("그러다 보니", "게다가", "하지만")가 자연스럽게 흐름을 이어주는가?
8. 감정이나 생각을 솔직하게 드러내는 문장이 있는가? 너무 건조하지 않은가?
9. 기술 포스트라면: 문제 → 시도 → 한계 → 해결 → 회고 구조를 따르는가?
10. 회고 글이라면: 사건 → 내 느낌 → 배움 순서로 풀었는가?

## 8. 주의할 점 (작성자의 약점 / 의식할 부분)

가이드를 그대로 따르되, 아래 함정에 빠지지 않도록 유의한다.

- **너무 말이 늘어지는 경향이 있다.** 긴 문장을 쓸 때도 한 문장 안에서 주제가 세 번 이상 바뀌지 않도록 한다.
- **"정말로", "너무나도" 같은 강조 부사를 남발하면 인상이 약해진다.** 한 문단에 한두 번만 쓴다.
- **감정 서술이 회고 글에 과도하게 몰리면 통찰이 묻힌다.** 감정을 쓴 뒤에는 반드시 "그래서 뭘 배웠는지"를 붙인다.
- **기술 포스트에서 자기 자랑처럼 보일 수 있다.** 자랑하고 싶은 마음은 글 끝 "결론" 섹션에 몰아 넣고, 본문은 문제 해결 중심으로 유지한다.
- **ai가 작성한 느낌의 문장을 절대 사용하지 않는다.**

  - ~의 진짜 의미
  - (a)가 (b)의 본질이다.
  - 본질은 ~이다.
  - ~~를 관통하는
  - 놀랍도록
  - 의외로 정교하다.
  - 정체가 이것이다
  - 이 설명은 거의 확실하다
  - 원리(원칙, 본질)은 단순하다.
  - ~하는 이유가 여기에 있다.
  - 중요한 것은 ~ : 문단에서 가장 중요한 문장이 아니라면 사용하지 않기. 가장 중요하다고 해서 무작정 사용하지도 말기
  - 이 차이는 단순한 ~이 아니라 ~~에 대한 답이다.
  - ~~이 진짜 내용이다.
