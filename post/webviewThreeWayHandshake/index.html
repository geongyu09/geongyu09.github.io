웹뷰와 네이티브 앱 간의 통신

우선 웹뷰를 띄우기 위해서는 Webview 라이브러리를 사용하는 방법이 가장 대중적이다.

웹뷰를 사용할때에는 Webview 컴포넌트에 보여주고싶은 웹의 주소를 source로 넘겨주면 된다.

js는 웹과 앱 두 환경에서 돌아가지만, 결국 하나의 서비스를 이루게 된다. 이에 따라서 하나의 통일된 사용자 경험을 주는 것이 중요하다. 이를 위해 웹과 앱은 서로 필요한 정보들을 소통해야 하는 상황들이 많이 발생한다. 웹뷰와 네이티브 앱 간의 통신을 위해서는 아래와 같은 방식을 사용할 수 있다.

웹과 앱이 서로 메시지를 주고 받는 것은 정말 코드 몇 줄로 간단히 구현이 가능하다. 하지만 실제 서비스를 개발하다보면 정말 많은 경우를 고려해야만 한다.

기존 이벤트 기반 통신의 문제점들

아직 앱 개발을 많이 해보지 않은 짧은 식견으로 생각한 문제점은 다음과 같다.

  1. 웹과 앱 간의 메시지 형식을 정하기 어렵다.
  2. 이벤트 기반 코드들은 전부 리액트와 생명 주기가 맞지 않는 사이드 이팩트들이다.
  3. 앱에서 웹으로 메시지를 보내는 경우, 웹이 로딩되지 않은 상태에서 메시지를 보내면 메시지를 받지 못한다.
  4. 서로간의 통신에서 response가 존재하지 않아 전달이 올바르게 되었는지, 혹은 에러가 발생했는지를 알 수가 없다.

분명히 나 뿐만 아니라 다른 개발자들도 동일하게 느꼈을 것이라 생각한다. 그러하여 다양한 라이브러리를 찾아보았는데, 생각보다 라이브러리가 많지 않았다. 정말 잘 만들어진 FE conf 에서 발표된 라이브러리가 있었지만, 앱을 처음 개발하는 나의 입장에서는 가볍게 나에게 필요한 기능만을 제공하는 나만의 코드가 있기를 바랬다. 그리하여 직접 라이브러리를 개발하기로 하였다.

(새로운 라이브러리를 또 공부해서 사용하는 것 보다는 내가 필요한 기능만을 가진 가벼운 라이브러리를 만드는 것이 시간적, 개발적으로나 훨씬 비용이 적게 들 것으로 예상하였다!)

라이브러리 개발
라이브러리의 목표

라이브러리의 목표는 웹과 네이티브 앱 간의 통신 로직을 간단하게 작성할 수 있도록 도와주는 것이다. 이를 위해 다음과 같은 기능을 제공하고자 한다.

  1. 메시지 타입 정의: 웹과 앱 간의 메시지 타입을 정의할 수 있는 기능을 제공한다. 정한 타입을 통하여 메시지의 형식을 일관되고, 타입 세이프하게 관리할 수 있다.
  2. 리액트 훅 사용: 리액트 훅을 사용하여 메시지를 보내고 받을 수 있는 간단한 API를 제공한다. 이를 통해 개발자는 복잡한 사이드 이팩트 관리 없이 메시지를 주고 받을 수 있다.
  3. 응답 처리: 메시지를 보낸 후 응답을 받을 수 있는 기능을 제공한다. 이를 통해 메시지가 올바르게 전달되었는지 확인할 수 있다.
  4. 에러 처리: 메시지 전송 중 발생할 수 있는 에러를 처리할 수 있는 기능을 제공한다. 이를 통해 개발자는 에러 상황을 쉽게 처리할 수 있다.
  5. 통신 가능 시점 관리: 웹이 로딩된 후에만 메시지를 보낼 수 있도록 관리한다. 이를 통해 웹이 로딩되지 않은 상태에서 메시지를 보내는 문제를 해결할 수 있다.

위의 목표들은 흔히 웹에서 생각할 수 있는 HTTP 통신과 유사하다. 그래서 이를 구현하기 위해서는 HTTP 통신을 구현하는 것과 유사한 방식으로 개발하면 될 것이라 생각했다.

통신 가능 시점 확인하기
해결해야하는 문제 상황

개발하다보면 웹을 띄우자마자 특정 동작을 해야하는 경우가 존재한다. 뿐만 아니라 어느 시점부터 웹과 앱 간의 통신이 가능한지 확인해야만 안정적으로 메시지를 주고 받을 수 있을 것이다.

처음에는 단순히 웹뷰가 로딩된 후(Webview 컴포넌트의 onLoad 사용)에만 메시지를 보내는 방법을 생각했다. 하지만 이는 웹뷰가 로드되었다는 것을 알려줄 뿐 정말로 앱에서 보낸 메시지를 받을 수 있는 Next.js의 js가 올바르게 로드되었는지를 나타낼 수는 없었다. 그렇기에 대부분의 경우 올바르게 동작하지 않았다.

아이디어 : TCP 3-Way-Handshake

어떻게 이 문제를 해결할 수 있을까 고민하다가 TCP 통신을 생각해보았다.

  • 통신을 시작하는 주체가 먼저 SYN 세그먼트를 보낸다.
  • 상대방은 SYN 세그먼트를 받고, SYN/ACK 세그먼트를 보낸다.
  • 마지막으로 주체는 ACK 세그먼트를 보내며 연결을 완료한다. 이때 ACK와 동시에 데이터를 보낼 수 있다.

이러한 3-Way-Handshake 과정을 통해 각자 통신에 필요한 준비가 완료되었음을 알 수 있다.

이를 웹뷰 통신 로직에 적용해볼 수 있지 않을까?

개발 과정

처음에는 웹뷰에 javascript를 삽입(inject)하여, 웹뷰가 로딩되면 바로 메시지를 보내는 방식으로 구현 하고자 하였다. 이를 통해서 굳이 웹에서는 앱과의 통신에 대해서 신경쓰지 않으며, 앱 내에서만 통신을 관리할 수 있을 것이라 생각했다.

하지만 이 방법은 웹뷰가 로딩되기 전에 메시지를 보내는 문제가 발생했다. 이를 해결하기 위해서 웹뷰가 완전히 로딩 되어 js가 동작할 수 있는 시점을 직접 웹에서 알려주도록 하였다. 웹에서 앱으로 메시지를 보낸다는 것은, javascript가 완전히 로딩되었다는 것을 의미하며, 그 시점 이후부터는 앱으로부터 메시지를 받을 수 있다는 것을 의미한다. (Next를 기준으로 생각해보면, hydration이 완료된 이후(window를 사용할 수 있는 시점부터)라고 생각할 수 있다.)

HTTP로 생각해보면 앱은 항상 실행되고 있는 서버이고, 웹은 중간중간 간혈적으로 접속을 하고 끊기는 클라이언트라고 생각할 수 있다. 즉 어쩌면 웹이 먼저 메시지를 보내는 것은 자연스러운 것이다.

앱에서는 웹으로부터 syn 메시지를 받으면 syn/ack 메시지를 보내고, ack 메시지를 받으면 웹뷰가 준비되었다는 것을 인지한다. 이 과정이 전부 끝나면 웹뷰가 준비되었다는 것을 인지하게 된다.

나머지 문제들 해결

이제 웹뷰가 로딩된 이후에만 메시지를 보낼 수 있게 되었으니, 나머지 문제들을 해결해보자. 안전한 통신을 위하여 통신 가능 시점을 TCP 3-Way-Handshake로 확인하는 과정을 거쳤다. 이제는 이 메시지를 주고 받을 수 있도록, 실제 HTTP 통신에서 메시지를 하위 레이어의 헤더로 감싸 보내듯이 인자로 전달받은 메시지를 헤더로 감싸서 보내도록 하였다.

받을 때에는 컴포넌트로, 보낼 때에는 훅으로

웹뷰와 앱 간의 메시지를 주고 받을 때, 받는 쪽은 컴포넌트로, 보내는 쪽은 훅으로 구현하였다. 이는 리액트의 컴포넌트와 훅의 사용 방식을 따르도록 하여 개발자가 쉽게 사용할 수 있도록 하였다.

타입 안정성을 챙기자

흔히 개발자가 api 명세서를 작성할 때 요청과 응답값을 팀의 취향에 맞게 정의한다. 메시지 타입 또한 사용하는 곳에서 직접 정의할 수 있도록 하는 것이 맞다고 생각하였다. 정의한 타입을 지킬 수 있도록 하여 타입 세이프한 통신이 가능하게 하고자 하였다.

웹의 경우 아래처럼 사용하도록 하였다.

  • useBridge 훅을 통해서 요청을 보낼 수 있는 함수를 얻어올 수 있다.
  • useBridge 훅에 요청과 응답 메시지 타입을 제네릭으로 넘겨주어, 요청과 응답 메시지의 타입을 미리 정의할 수 있다.
  • request 함수의 경우 보낼 요청 메시지와, 요청에 대한 응답을 받았을 때 호출할 콜백, 에러가 발생했을 때 호출할 콜백을 인자로 받는다. 각각은 이전에 정의한 메시지 타입을 따른다.
  • BridgeRequestListener 컴포넌트에 요청과 응답 메시지 타입을 제네릭으로 넘겨주어, 요청과 응답 메시지의 타입을 미리 정의할 수 있다.
  • onRequest 콜백을 통해서 요청 메시지를 받을 수 있다. 요청 메시지는 이전에 정의한 요청 메시지 타입을 따른다. 해당 콜백의 반환값은 응답 메시지가 되며, 필수적으로 응답 메시지를 반환해야 한다.

앱의 경우 아래와 같이 사용하도록 하였다.

  • usePostMessageBridge 훅을 통해서 메시지를 보낼 수 있는 postMessage 함수와 ref를 얻어올 수 있다.
  • usePostMessageBridge 훅에 요청과 응답 메시지 타입을 제네릭으로 넘겨주어, 요청과 응답 메시지의 타입을 미리 정의할 수 있다.
  • postMessage 함수의 경우 보낼 요청 메시지를 인자로 받는다. 요청 메시지는 이전에 정의한 요청 메시지 타입을 따른다.
  • ref는 Webview 컴포넌트에 전달해주어야 한다. 이를 통해서 Webview 컴포넌트에서 메시지를 보낼 수 있다.
  • WebviewWithBridge 컴포넌트에 요청과 응답 메시지 타입을 제네릭으로 넘겨주어, 요청과 응답 메시지의 타입을 미리 정의할 수 있다.
  • onBridgeMessage 콜백을 통해서 요청 메시지를 받을 수 있다. 요청 메시지는 이전에 정의한 요청 메시지 타입을 따른다. 해당 콜백의 반환값은 응답 메시지가 되며, 필수적으로 응답 메시지를 반환해야 한다.

여기서 웹은 요청에 대한 응답을 콜백으로 받는 반면, 앱은 요청에 대한 응답을 반환값으로 받는다는 차이가 있다. 이는 Webview 컴포넌트의 ref로는 응답을 처리할 수 없는 구조이기 때문에 불가피하게 모든 응답 혹은 요청은 WebviewWithBridge 컴포넌트로 받아야만 한다.

요청과 응답

이와 더불어서 보낸 요청에 대한 응답을 받을 수 있도록 해야 했다. 단방향인 이벤트 기반의 통신에서, 받는 값이 요청인지 응답인지를 구분할 수 있어야만 했고, 응답이라면 어떤 요청에 대한 응답인지를 구분해야만 했다. 이를 구분하기 위하여 조금 더 명확하게 메시지 타입을 정의하도록 하였다.

모든 메시지는 고유한 식별자 id를 가진다. 요청이라면 ack값이 null이고, 응답이라면 ack값이 요청 메시지의 _id값이 되도록 하였다. 이를 통해서 요청과 응답을 구분할 수 있고, 어떤 요청에 대한 응답인지를 특정지을 수 있었다.

메시지 큐

이제 메시지의 형식이 정해졌고, 요청과 응답을 주고 받을 수 있게 되었다. 이제는 메시지를 보내는 쪽에서 요청에 대한 응답을 받아 처리할 수 있도록 해야 했다. 응답은 요청을 보낸 즉시 오지 않는 비동기 방식으로 동작하기 때문에, 요청을 보낼 때마다 응답을 처리할 콜백을 미리 저장해두고, 응답이 왔을 때 해당 콜백을 찾아 호출해야만 했다. 이를 위해서 메시지 큐를 구현하였다. 요청을 보낼 때마다 메시지 큐에 요청 메시지의 _id와 응답 콜백을 저장해두고, 응답 메시지를 받았을 때 메시지 큐에서 해당 _id에 대한 콜백을 찾아 호출하는 방식으로 구현하였다.

큐의 이름은 TCP 통신에서 흐름 제어를 위해 사용하는 수신 윈도우(RWND, Receive Window)에서 따왔다.

RWindow 인스턴스를 전역으로 생성하여 id와 콜백을 관리하도록 하였다. 요청을 보낼 때마다 RWindow 인스턴스에 id값과 콜백을 저장하도록 하였다.
