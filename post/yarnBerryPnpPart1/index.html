[Yarn PnP] 1편. 패키지 매니저와 Yarn Berry

TypeScript 7이 Yarn Berry의 PnP 환경에서만 동작하지 않았던 경험을 계기로, 패키지 매니저가 하는 일과 lock 파일의 역할, 그리고 Yarn Berry가 node_modules 대신 PnP를 택한 이유를 정리하였습니다.

1편. 패키지 매니저란?

Yarn Berry와 PnP를 공부하게 된 계기

우아한테크코스에서 레벨 3 팀 프로젝트를 준비하면서 Yarn Berry의 PnP(Plug'n'Play) 방식을 직접 경험해 보고 싶어, TypeScript와 Yarn Berry로 개발 환경을 구축하고자 했다.

하지만 최근에 출시된 TypeScript 7버전과 함께 사용하려고 하자 아래와 같은 오류가 발생했다.

같은 프로젝트를 pnpm으로 설치했을 때는 TypeScript 7이 정상적으로 동작했기 때문에, 나는 코드나 tsconfig.json의 설정이 잘못된 것이 아니라 PnP 방식에서만 생기는 문제라고 판단했다. pnpm처럼 node_modules 폴더를 만드는 패키지 매니저에서는 동작하는데 PnP에서만 사용할 수 없다면 PnP가 전혀 다른 방식으로 패키지를 찾고 있다고 볼 수 있다. 결국 우리팀은 Yarn Berry 대신 pnpm으로 바꿔서 진행하게됐지만, PnP에서만 TypeScript 7이 동작하지 않은 원인을 모른 채 그냥 넘어가고 싶지 않아서 나는 "Yarn Berry는 어떻게 PnP를 구현했을까?"라는 질문에 답을 하기 위한 공부를 진행하게됐다.

패키지 매니저가 어떤 역할을 하는걸까?

패키지 매니저란 무엇일까?

패키지 매니저는 소프트웨어 패키지를 설치, 업데이트, 삭제하는 과정을 자동으로 처리하면서 패키지 사이의 의존 관계와 버전을 기록해 두어, 어느 환경에서 설치해도 같은 패키지 구성이 만들어지도록 관리하는 도구를 말한다.

운영체제의 apt나 Homebrew, Python의 pip처럼 언어와 환경마다 패키지 매니저가 있으며, JavaScript & node 진영에는 npm, Yarn, pnpm, bun 등이 있다.

아마 프론트엔드 개발을 하게 되면 패키지매니저의 명령어와 node환경이 자주 사용하는 부분에 한정해서는 하루에도 수십번 명령어를 입력해왔을 것이기에 정말 익숙할 것이다.

npm install을 입력하면 무슨 일이 일어날까?

그런데 막상 npm install을 실행했을 때 npm이 어떤 순서로 무슨 일을 하는지 설명해 보라고 하면, "패키지를 설치한다" 말고는 선뜻 대답하기 어렵다.

package.json에는 "react": "^19.0.0"처럼 패키지 이름과 버전 범위만 적혀 있기 때문에, npm은 레지스트리에 패키지 정보를 요청하고, 전달받은 정보들 중 범위에 맞는 버전 가운데 하나를 선택하여 설치한다.

레지스트리란?

레지스트리는 개발자가 npm publish로 올린 패키지를 이름과 버전별로 모아 두고, 패키지 매니저가 요청하면 패키지 정보와 파일을 내려주는 서버(https://registry.npmjs.org)를 말한다.

https://registry.npmjs.org/[패키지명]으로 요청하면 패키지의 모든 버전 목록과 버전별 의존성 정보를 담은 JSON 메타데이터를 받아올 수 있다.
npm은 메타데이터의 버전 목록에서 package.json에 기록된 범위에 맞는 버전을 고른다.
고른 버전의 메타데이터에는 https://registry.npmjs.org/react/-/react-19.0.0.tgz 같은 tgz 주소와 파일의 해시도 함께 적혀 있어서, npm은 해당 주소로 tgz 파일을 내려받는다.

Yarn의 기본 주소인 https://registry.yarnpkg.com도 npm 레지스트리와 같은 데이터를 전달하는 프록시 주소이다.

설치하고자 하는 패키지 또한 자신의 의존성을 가질 수 있다. 그리고 이 의존성까지 설치해야 비로소 패키지가 올바르게 동작할 수 있다.

그래서 패키지들의 package.json에 작성된 하위 의존성의 버전도 같은 방식으로 확정해나가면서 새로운 의존성이 더 나오지 않을 때까지 확정 과정을 재귀적으로 반복한다.

모든 버전을 확정한 뒤에야 npm은 패키지마다 tgz 파일을 내려받아 node_modules 폴더에 압축을 풀어 놓으며, 마지막으로 확정한 결과를 lock 파일인 package-lock.json에 기록한다.

만약 이미 lock 파일이 있다면 npm은 레지스트리에서 버전을 고르는 과정을 생략하고 lock 파일에 적힌 버전을 사용한다.

tgz 파일과 zip 파일

.tgz 확장자는 .tar.gz를 줄여 쓴 이름이며, 여러 파일을 tar로 한 파일에 차례대로 이어 붙인 뒤 결과 전체를 gzip으로 한 번에 압축해서 만든다. npm pack으로 만든 패키지 파일을 풀면 모든 파일이 package/ 폴더 아래에 들어 있고, 레지스트리는 패키지의 버전마다 이렇게 만든 tgz 파일 하나를 제공한다.

tar는 각 파일의 헤더와 내용을 앞에서부터 순서대로 이어 붙일 뿐 전체 목록을 담은 색인이 없고 gzip이 아카이브 전체를 한 덩어리로 압축하기 때문에, tgz 안의 파일 하나를 읽으려면 파일 맨 앞부터 해당 위치까지 모두 압축을 풀어야 한다. 반대로 흔히 사용하는 zip 압축 형식은 파일마다 따로 압축하고 파일 끝의 중앙 디렉터리에 모든 항목의 이름, 위치, 크기를 기록해 두기 때문에, 중앙 디렉터리만 읽으면 원하는 파일의 위치로 바로 이동해서 해당 파일만 풀 수 있다.

npm이 tgz를 쓰는 이유는 패키지를 설치할 때 파일 하나를 골라 읽을 일이 없고 전부 node_modules에 풀어 놓기만 하면 되기 때문이며, tgz는 앞에서부터 순서대로 읽는 형식이라 내려받는 도중에 압축을 풀기 시작할 수 있고, 비슷한 텍스트 파일이 많은 JavaScript 패키지는 여러 파일을 한꺼번에 압축하는 gzip에서 더 작아지며, tar가 유닉스의 실행 권한까지 기록하므로 bin 파일을 그대로 옮길 수 있다.

Yarn Berry의 PnP는 압축을 풀지 않은 채 실행 중에 필요한 파일만 골라 읽어야 하기 때문에 받은 tgz를 zip으로 다시 묶어서 저장하는 방식을 택했다.

package.json에 작성된 패키지들의 의미

npm이 버전을 확정할 때 출발점으로 삼는 package.json에는 의존성을 쓰임새에 따라 나누어 적는다.

  • dependencies에는 앱을 실행할 때 필요한 패키지를 적는다.
  • devDependencies에는 TypeScript나 Vite처럼 개발하고 빌드할 때만 필요한 패키지를 적는다.
  • peerDependencies에는 라이브러리가 직접 설치하지 않고, 라이브러리를 사용하는 프로젝트에 설치되어 있기를 기대하는 패키지를 적는다. React 컴포넌트 라이브러리가 react를 peerDependencies에 적어 두면, 라이브러리는 자기만의 React를 따로 들고 오지 않고 프로젝트에 설치된 React를 함께 사용하게 된다.

위처럼 버전은 정확한 번호 대신 범위로 적는 경우가 많으며, npm install react로 패키지를 추가해도 npm은 버전 앞에 ^를 붙인 범위로 package.json에 기록한다.

^ 는 기준 숫자 이상부터 0이 아닌 가장 앞자리가 변경되지 않는 범위의 패키지를 선택한다.
예를 들어 ^0.2.3은 0.2.3이상 0.3.0 미만까지만 허용한다.

~ 는 기준 숫자 이상부터 앞의 두 자리인 메이저 버전과 마이너 버전이 변경되지 않는 범위의 패키지를 선택한다.
예를 들어 ~1.2.3은 1.2.3 이상 1.3.0 미만까지만 허용하므로, 2.0.0 미만까지 허용하는 ^1.2.3과 달리 마지막 자리인 패치 버전만 올라갈 수 있다.

표기허용하는 범위설치되는 버전
^19.0.019.0.0 이상 20.0.0 미만19.x.x 안의 최신 버전
~19.0.019.0.0 이상 19.1.0 미만19.0.x 안의 최신 버전
19.0.019.0.019.0.0

그런데 package.json에는 범위만 적혀 있으므로, 같은 package.json으로 설치하더라도 설치한 날짜에 따라 다른 버전이 들어올 수 있다. "react": "^19.0.0"이라고 적어 둔 프로젝트를 React 19.1.0이 나오기 전에 설치한 팀원은 19.0.x를, 나온 뒤에 설치한 팀원은 19.1.x를 받을 수 있다는 것이다.

package.json에 적을 패키지의 버전을 19.0.0 처럼 작성하여 고정하더라도 설치하는 패키지의 하위 의존성 package.json에 적힌 범위까지는 고정할 수 없기 때문에 이를 package.json 파일만으로는 완벽한 환경 통제를 할 수 없다.

어제 내 컴퓨터에서 잘 돌던 코드가 오늘 갑자기 깨질 수도 있다는 건데, 그렇다면 시간이 지나도 모두가 같은 버전을 설치하게 하려면 어떻게 해야 할까?

lock 파일에는 무엇이 기록될까?

lock 파일에는 패키지마다 확정한 정확한 버전과 tgz를 내려받을 주소인 resolved, 내려받은 파일이 바뀌지 않았는지 검사하는 해시인 integrity가 기록된다.

npm은 resolved의 주소에서 받은 파일의 해시가 integrity와 다르면 설치를 멈추기 때문에, 레지스트리나 중간 네트워크에서 모종의 이유로 파일이 변경돼 잘못 설치되는 경우를 막는다.

lock 파일을 저장소에 커밋해 두면 팀원과 CI도 lock 파일에 적힌 버전을 설치하게 된다. lock 파일이 있으면 npm install 을 했을 때 package.json의 범위를 만족하는 한 lock 파일의 버전을 먼저 사용하지만, package.json을 수정했다면 범위를 다시 해석해서 lock 파일을 갱신하기도 한다.

(npm install 에서의 영향력 : package.json > lock)

npm ci 명령어도 npm install 과 결과물만 봤을 땐 비슷한 동작을 한다. 동작에서의 차이라면 node_modules를 지운 뒤 package.json의 범위를 다시 해석하지 않고 lock 파일에 적힌 버전으로만 설치한다. 만약 package.json과 package-lock.json 파일의 내용이 서로 맞지 않으면 lock 파일을 고치지 않고 오류를 내며 멈추기 때문에 CI에서는 주로 npm install 이 아닌 npm ci를 사용한다.

( npm ci 에서의 영향력 : package.json < lock)

지금은 npm install만 실행해도 package-lock.json이 생기지만, npm이 처음부터 lock 파일을 자동으로 만들어 주지는 않았다고 한다. 예전 npm에서 버전을 고정하려면 npm shrinkwrap을 직접 실행해서 npm-shrinkwrap.json을 만들어야 했고 실행하지 않으면 lock 파일이 생기지 않았다. 이러한 문제점들을 인식하고Facebook은 설치할 때마다 lock 파일을 자동으로 만드는 Yarn을 공개했다.

Yarn classic의 등장

이런 npm과는 다르게 Yarn 1은 설치할 때마다 yarn.lock을 자동으로 만들어서, 같은 package.json으로 언제 설치하더라도 lock 파일에 적힌 버전을 받도록 했다. 2016년 당시의 npm은 lock 파일을 기본으로 만들지 않았기 때문에 설치할 때마다 결과가 달라질 수 있었고, 설치 속도도 느렸으며, 한 번 받아 본 패키지도 설치할 때마다 네트워크에 다시 요청해야 했다.

Facebook이 공개한 Yarn 1은 lock 파일 말고도 npm의 불편을 덜어 주는 기능을 함께 갖추고 나왔다. 여러 패키지의 요청을 병렬로 처리해서 동시에 내려받았고, 한 번 받은 패키지를 전역 오프라인 캐시에 저장해 두었다가 다음 설치부터는 네트워크 없이 캐시에서 꺼내 썼으며, 패키지의 코드를 실행하기 전에 체크섬으로 내려받은 파일이 바뀌지 않았는지 검증했다.

하지만 Yarn 1도 npm과 같이 의존성을 node_modules 최상위로 끌어올려 평평하게 풀어 놓는 호이스팅 방식으로 폴더를 만들었기 때문에, 선언하지 않은 패키지를 불러올 수 있는 유령 의존성 문제와 설치할 때마다 수만 개의 파일을 복사해야 하는 비용은 해결하지 못했다.

node_modules 방식에는 어떤 문제가 있을까?

Yarn 1까지도 해결하지 못한 문제들은 모두 패키지를 node_modules 폴더에 풀어 놓는 방식에서 생긴다.

  • 설치 시간의 대부분을 패키지마다 tgz의 압축을 풀어서 수만 개의 파일을 디스크에 복사하는 I/O 작업에 쓴다.
  • 호이스팅으로 최상위에 올라온 패키지는 package.json에 선언하지 않았더라도 require나 import로 불러올 수 있으며, 선언하지 않은 패키지에 기대어 동작하던 코드는 다른 패키지를 업데이트하다가 해당 패키지가 최상위에서 빠지면 갑자기 깨진다. 이렇게 선언하지 않은 패키지에 의존하게 되는 문제를 유령 의존성 이라고 부른다.
  • 호이스팅으로 node_modules의 크기를 줄이더라도 서로 다른 버전을 요구하는 패키지가 섞인 의존 관계에서는 같은 패키지가 여러 위치에 중복 설치되며, Node는 두 위치의 패키지를 서로 다른 모듈로 불러오기 때문에 React처럼 인스턴스가 하나여야 하는 패키지에서는 오류가 생기기도 한다.

패키지를 node_modules 폴더에 풀어 놓는 방식인 호이스팅을 하는 이유에 대해서는 2편에서 자세히 다룬다.

Yarn Berry는 무엇을 바꿨을까?

Yarn Berry는 node_modules의 모양을 고치지 않고, node_modules 폴더를 아예 만들지 않는 방법을 택했다.

Yarn 공식 문서의 Plug'n'Play 페이지에 따르면 Yarn PnP는 node_modules 폴더 대신 .pnp.cjs라는 Node.js 로더 파일 하나를 만들고, 해당 파일에 프로젝트의 의존성 트리 전체 정보를 담아서 도구들에게 패키지가 디스크의 어디에 있는지와 require, import 호출을 어떻게 해석해야 하는지를 알려 준다.

공식 문서는 pnpm처럼 node_modules를 더 똑똑하게 배치하는 알고리즘으로도 일부 문제는 해결할 수 있지만 모든 문제를 해결할 수 있는 방식은 PnP뿐이라고 설명하면서 PnP의 장점을 소개하는데, 각 장점을 앞에서 정리한 node_modules 방식의 문제와 짝지어 본다.

Minimal install footprint 항목은 설치에 드는 비용을 다룬다. npm은 파일을 디스크의 다른 위치로 복사하는 데, pnpm은 심볼릭 링크와 하드 링크를 만드는 데 설치 시간의 상당 부분을 I/O 작업에 쓰지만, PnP 설치는 대부분 .pnp.cjs 로더 파일을 생성하는 것으로 끝난다.

Shared installs across disks 항목은 앞의 장점과 이어진다. pnpm은 전역 저장소에 있는 패키지의 파일마다 하드 링크를 만들어서 최종 위치에 연결해야 하지만, PnP 로더는 캐시에 있는 패키지의 경로를 직접 가리키기 때문에 디스크에 있는 모든 프로젝트가 같은 패키지 파일을 함께 사용한다.

Perfect and correct hoisting 항목은 중복 설치 문제와 짝을 이룬다. 일반적인 node_modules 설치는 유령 의존성의 위험을 감수하면서까지 호이스팅으로 폴더의 크기를 줄이려고 하지만, 일부 의존 관계에서는 안전하게 끌어올릴 수 없어서 같은 패키지가 중복 설치되고 여러 번 인스턴스화된다. PnP는 폴더를 배치하지 않고 .pnp.cjs에 기록한 의존 관계로 패키지를 찾기 때문에 이런 문제가 생기지 않는다.

Ghost dependencies protection 항목은 유령 의존성을 다루는데, Yarn은 모든 패키지와 각 패키지의 의존성 목록을 알고 있으므로 패키지가 선언하지 않은 의존성에 접근하면 막는다. 공식 문서도 다른 패키지 매니저에서 문제없이 동작하던 코드가 PnP에서는 오류를 낼 수 있어서 PnP를 도입하기 어렵다는 점을 인정하지만, 조금 번거롭더라도 오늘 동작하는 앱이 관련 없는 의존성을 추가하거나 업데이트하다가 나중에 갑자기 깨지는 일은 없다고 설명한다.

Semantic erroring 항목은 오류 메시지를 다룬다. Node는 잘못된 require나 import를 만나면 Cannot find module처럼 원인을 알기 어려운 오류만 던지지만, PnP는 어떤 패키지가 무엇을 선언하지 않고 접근했는지까지 알려 준다.

공식 문서의 Caching 페이지는 PnP와 함께 쓸 수 있는 Zero-Installs도 소개한다. .yarnrc.yml에서 enableGlobalCache를 false로 설정하면 Yarn은 패키지의 zip 캐시를 프로젝트 안의 .yarn/cache 폴더에 저장하는데, 이 캐시와 .pnp.cjs를 함께 저장소에 커밋해 두면 clone하거나 브랜치를 바꾼 직후에도 yarn install 없이 프로젝트를 실행할 수 있다.

.pnp.cjs는 어느 컴퓨터에서 만들어도 내용이 같고 캐시에는 로더가 가리키는 파일이 모두 들어 있기 때문에, git checkout이 yarn install의 역할까지 하게 된다. node_modules 폴더를 커밋해도 비슷한 효과를 낼 수는 있지만, Git이 수천 개의 파일을 하나씩 비교해야 하고 호이스팅 때문에 파일 위치도 자주 바뀐다. 반면 PnP 캐시는 패키지마다 zip 파일이 하나씩만 있어서 Git이 추적하기 훨씬 쉽다. 단, 네이티브 의존성이 있는 패키지는 zip 안에서 바로 실행할 수 없기 때문에 이런 패키지를 추가하거나 지울 때는 yarn install을 꼭 실행해야 한다.

처음에는 TypeScript 7이 PnP에서만 모듈을 찾지 못한 원인을 알고 싶어서 시작한 공부였는데, 1편을 정리하고 나니 Yarn Berry가 PnP를 만든 이유는 이해했지만 PnP가 실제로 패키지를 어떻게 찾아 주는지는 아직 설명할 수 없었다.

다음 글에서는 어떻게 Yarn Berry가 node_modules 폴더 없이 패키지를 불러오는지 알아보기 전에, node_modules가 있을 때 Node.js가 require를 만나면 어떤 순서로 모듈을 찾고 실행하는지부터 따라가 보려고 한다. Node.js가 상위 폴더로 거슬러 올라가며 node_modules를 탐색하는 방식을 알고 나면, 패키지 매니저가 왜 호이스팅을 하는지와 유령 의존성이 왜 생기는지도 함께 이해할 수 있다.
